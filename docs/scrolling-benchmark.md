# Scrolling benchmark in IntelliJ

The benchmark opens a separate **Varro Benchmark** tool window in the current IDE. It runs the vendored OpenJet UI with a synthetic, in-memory host served over loopback. It does not connect the fixture to OpenCode or modify existing chat sessions.

It measures browser rendering in JCEF, including native wheel input and automatic bottom-follow. It does not measure the ordinary Kotlin chat bridge, server transport, model latency, or production persistence.

The fixture displays **GPT Luna** as its model label. Output is generated locally, so these measurements make no model calls and incur no model cost. Use Luna for any separate live-model test runs.

## Start the fixture server

The diagnostic build reuses the upstream Varro E2E fixture generator. A sibling `varro` checkout is the default source. This dependency is only needed to run the benchmark, not to build or use the plugin.

From `webview/`:

```sh
npm ci --include=optional --no-audit --no-fund
npm run benchmark
```

For another checkout or port:

```sh
npm run benchmark -- --source /path/to/varro --port 4186
```

The script builds a production-minified fixture using **this repository's vendored UI**, prints a URL, and serves it on `127.0.0.1`. It records the upstream fixture revision and vendored UI revision in a manifest. Each invocation creates a fresh directory under `build/scroll-benchmark/`.

## Open it in an existing IDE

Install a plugin build containing this integration. Use Find Action and choose **Open Varro Scrolling Benchmark**, then enter the URL printed by the server. No separate IDE instance is required.

The page provides three run buttons:

- **manual**: records 10 seconds of actual wheel or transcript-key input.
- **automatic**: appends 120 Markdown paragraphs at 32 ms intervals and waits for bottom-follow to settle.
- **manual-streaming**: streams the same content while recording 10 seconds of manual interaction.

Controls hide during measurement. Keep the benchmark visible and avoid resizing during a run. Use **Reset fixture** between runs so prior streamed content does not accumulate. A manual run with no trusted wheel/key input or no scrolling is marked invalid.

The native **Open benchmark developer tools** button opens this view's JCEF DevTools. Record the Performance panel to inspect layout, paint, and scripting. The controller emits `varro-benchmark-stream-start` and `varro-benchmark-stream-complete` timing marks.

Useful fixture URLs:

| Query | Content |
| --- | --- |
| `?scenario=mixed-small-transcript` | 36 mixed messages |
| `?scenario=large-transcript` | 480-message dataset with normal fixture pagination |
| `?scenario=huge-content-transcript` | 180 messages with about 860K text characters |
| `?scenario=tool-cards-large-transcript` | 140 messages containing tool activity |
| `?scenario=huge-content-transcript&singleTall=1` | 40 messages with about 1 MB of text, mostly in a single response |

Append `&run=automatic` for a run that starts after initial rendering settles. These are text-character counts, not measured model-token counts.

## Launch from Gradle

From the repository root, after starting the fixture server:

```sh
./gradlew runIde \
  '-PscrollBenchmarkUrl=http://127.0.0.1:4186/?scenario=huge-content-transcript&singleTall=1' \
  -PscrollBenchmarkDebugPort=9222 \
  --args="/path/to/benchmark-workspace"
```

The opt-in startup hook opens the benchmark when the project opens. An ordinary IDE launch does nothing automatically. For Kotlin-only iteration with already-built browser assets, add `-PskipWebview=true`.

The page URL carries native provenance generated by the plugin: IDE PID, loaded class location,
plugin version, browser implementation, and frame-rate policy. Results retain that provenance and
hashes of the renderer, message-part component, message list, and affected stylesheets. Use
`node scripts/drive-scroll-benchmark.mjs --inspect` to inspect the current fixture without starting a run.

## Automated input and trace capture

JCEF's Chrome debugging endpoint must be available. In an existing IDE, its port is controlled by the `ide.browser.jcef.debug.port` registry setting; the Gradle command above sets it for the launched IDE. A registry change may require restarting JCEF or the IDE.

From `webview/`:

```sh
node scripts/drive-scroll-benchmark.mjs --mode manual --scenario large-transcript --trace
node scripts/drive-scroll-benchmark.mjs --mode automatic --scenario huge-content-transcript --single-tall --trace
node scripts/drive-scroll-benchmark.mjs --mode manual-streaming --scenario huge-content-transcript --single-tall --trace --screenshot
```

The driver uses Node's built-in WebSocket client. It requires exactly one fixture page on the specified origin, reloads only that page, and sends native CDP wheel input in manual modes. It leaves other JCEF pages alone. Use `--cdp http://127.0.0.1:9222` and `--origin http://127.0.0.1:4186` to override the defaults.

Each automated run saves `result.json` and, with `--trace`, `trace.json` in a fresh `build/scroll-benchmark/cdp-*` directory. `--screenshot` captures the viewport after timing stops. The fixture server also saves each result in its run's `results/` directory. Stop the fixture server with Ctrl+C when finished; close the benchmark tab independently of normal chats.

## Reading results

Results include actual browser and transcript viewport dimensions, browser user agent, fixture sizes, frame intervals, long tasks, sampled mounted row/node counts, scroll movement, native input counts, errors, visibility, and resize evidence.

`valid` checks run conditions and basic scrolling correctness. It is not a performance pass. `performanceNeedsReview` is true for missing long-task instrumentation, page errors, p95 frame intervals above 25 ms, or frame/long-task durations above 100 ms. Animation-frame intervals measure JavaScript callback cadence, not every frame presented by the compositor. Tracing and geometry sampling add overhead.

Automatic runs retain ResizeObserver errors in their results. Do not discard them to turn a failed run into a pass. Initial-load time is excluded. Each manual driver run traverses approximately 6,000 px up and down, not the entire dataset.

### Rendering mode caveat

The benchmark and `WebviewHost` use `JcefBrowserFactory`, which explicitly requests off-screen
rendering so the browser participates in Swing painting alongside IDE popups and tooltips.
Earlier builds requested windowed rendering. IntelliJ's out-of-process JCEF overrode that request;
the tested 2026.2 runtime logged:

```text
Trying to create windowed browser when remote-mode is enabled. Settings isOffScreenRendering=false will be ignored.
```

Do not infer the effective rendering mode or frame rate from the builder flag alone. The IDE's JCEF version and `ide.browser.jcef.osr.framerate` are relevant evidence when comparing Chromium and IntelliJ runs.

The factory now defaults to 60 fps when the registry has no positive override. It applies the rate
through both creation settings and the native OSR setter. In the tested remote runtime, creation
settings alone still yielded 33.3 ms animation-frame intervals; the native setter yielded 16.7 ms.
An explicit positive registry override is preserved. Windowed browsers do not receive the OSR setter.
For a native control run, `-PscrollBenchmarkFrameRate=0` leaves the native frame rate unset.

## September 14 fix verification

The same extreme fixture was tested in IntelliJ IDEA 2026.2.2, JCEF Chromium 144, with a 456 x 850
browser viewport and a 443 x 687 transcript viewport. Native provenance identified the actual
`RemoteBrowser`, plugin 0.1.6 in the development sandbox, and the loaded IDE PID.

Three fixes address separate costs:

- Apply the requested OSR frame rate through the native setter instead of relying on browser creation settings.
- Replace cross-segment Markdown `:has()` look-ahead with a renderer-maintained tail-tag attribute.
  Style recalculation in the measured extreme-case trace fell from about 1,033 ms to 98 ms.
- Retain the Markdown renderer when a text-part snapshot is replaced. Previously this could replace
  thousands of unchanged nodes at completion; the final trace had no long tasks and a maximum layout

## ResizeObserver follow-up

The next real-IDE sweep reproduced ResizeObserver errors in all ten streaming runs across five
fixtures. Observer instrumentation identified two writes during resize delivery:

- `prepareMeasuredEntrance` changed the height of its own observed animated element.
- `MessageList` applied whole-pixel row corrections in a microtask. Microtasks still run within
  resize delivery, so these writes invalidated the observed row and its shallower track.

Both updates now coalesce into animation-frame callbacks and cancel pending work on cleanup.
The entrance callback reads the latest content height when it runs. Errors remain part of benchmark
validity checks. The fixes live in the sibling Varro sources and the matching OpenJet vendored files.
The benchmark manifest now also hashes `lib/measured-entrance.ts`.

### Original 116.6 ms frame gap

The original `cdp-9t9mtk/trace.json` records a 130.5 ms wall-clock gap between animation callbacks
corresponding to the 116.6 ms animation-timestamp interval. During that interval, renderer tasks
were below 1 ms. The GPU process recorded an overlapping 162.910 ms task in
`gpu/command_buffer/service/scheduler.cc`, `TryScheduleSequence`, and a 161.545 ms Dawn worker task.
Their thread CPU times were only 1.908 ms and 1.670 ms respectively.

This points to a native graphics wait rather than a long webview JavaScript/layout task. The trace
does not establish the cause of the GPU wait, and the observer fix is not proof of a GPU fix.
The gap did not recur in the final matrix or the five targeted repeats.
